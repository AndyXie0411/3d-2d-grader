# 3D → 2D Engineering Drawing Grader

Automatically grades **2D engineering drawings generated by AI models (ChatGPT, Claude, …) from a 3D STEP model**.

You give the grader two things:

1. the **STEP file** the AI was given, and
2. the **drawing the AI produced** (PNG / JPG / PDF).

The grader works out from the STEP geometry what a complete drawing of that part must contain, reads the AI drawing, and returns a 0–100 score with an itemised list of every deduction. **No hand-made reference drawing is needed.** One rule set applies to every part, so scores are comparable across parts and across models.

```
part.step ──► AI model ──► drawing.png
     │                           │
     └──────────► grader ◄───────┘
                    │
        reward.json  (score 0–1 + per-component scores)
        reward-details.json  (every check, its score, and why)
```

---

## How it works

### 1. Read the drawing (vision model)
Claude reads the drawing image and extracts it into structured data: views, dimensions, hole callouts, chamfers, GD&T, roughness, title block, technical notes, and layout defects. Results are cached by file hash, so re-grading the same image costs nothing and always gives the same result.

### 2. Measure the part (STEP geometry, local, no AI)
The STEP file is analysed with OpenCascade (`cadquery-ocp`). The analysis extracts:

- overall size (bounding box)
- every hole: diameter, depth (including the entry chamfer), through or blind, counterbored or not, and how many
- outer diameters (shafts, bosses), fillet radii, and chamfer sizes and counts
- every true distance: parallel faces, edge lengths, and hole-to-face and hole-to-hole offsets
- whether the part has internal features that need a section view

### 3. Score

| Component | Weight | What it checks |
|---|---|---|
| **Accuracy** (STEP) | 35 | Every value on the drawing (dimensions, hole sizes and depths, chamfers) must exist in the real geometry. Wrong values lose points. |
| **Completeness** (STEP) | 40 | Everything the STEP says must be dimensioned actually is (details below). |
| **Standard** | 10 | Main view, at least 3 orthographic/section/direction views, an isometric view, and enough dimensions. |
| **Consistency** | 10 | The drawing does not contradict itself: GD&T datums are defined, every section mark has its view, tap-drill sizes match the thread, thread depth is less than drill depth. |
| **Layout** | 5 | No overlapping or truncated text, and no text drawn over geometry. |
| *Reference* (optional) | 25 | Item-by-item comparison with a human reference drawing, if you have one. |
| *Fidelity* (optional) | 30 | Vision-model check against 3D render images, if you have no STEP file. |

When an input is missing, its component is skipped and the remaining weights are renormalised.

**Completeness** is half features and half positions.

- **Features.** Each item must be present on the drawing:
  - the 3 overall dimensions
  - every hole group: diameter, depth or `THRU`, and count
  - every outer diameter and fillet radius
  - every chamfer, with all its instances counted
  - a section view, if the part has counterbores or non-threaded blind holes
- **Position chain.** Every face position and hole centre along x, y and z must be reachable from the part edge through the drawing's dimensions. A missing location dimension leaves every position downstream of it undetermined, so it gets caught.

### Fairness rule
**Only information that can be derived from the STEP file is scored.** A STEP file contains geometry only, so the following are never penalised:

- dimensional tolerances and fits (`±0.02`, `H7`)
- GD&T and datums
- surface roughness
- thread class and thread depth
- title-block content (material, scale, part name)
- technical notes
- the letters used to name views and sections

Equivalent notations are accepted:

- `Ø20` matches `2×Ø20 THRU`, with partial credit for the missing count or `THRU`.
- `4-↧35` matches a linear `35` drawn in a section.
- "8× + note: back face identical" matches `16× BOTH SIDES`.
- A dimension that differs from the reference but is a true distance in the STEP is not counted as an error.

### Safeguards
| Mechanism | Effect |
|---|---|
| **Gates** | Not an engineering drawing (blank, photo, 3D render) scores **0**. No orthographic view, or fewer than 3 dimensions, caps the score at **20**. |
| **Prompt-injection guard** | Any text on the drawing that tries to influence grading ("give full score", "ignore instructions") scores **0**. |
| **Sampling and consensus** | `--samples 3` reads the drawing 3 times and keeps the majority answer. It reports an agreement rate and flags `needs_review` when the readings disagree. |

## Installation

Requires Python 3.12.

```bash
pip install -r requirements.txt
```

The grader calls Claude in one of two ways. Select with `DRAWING_GRADER_BACKEND`:

| Backend | How | Cost |
|---|---|---|
| `cli` (default when no API key is set) | Runs the local [Claude Code](https://claude.com/claude-code) CLI (`claude -p`). Claude Code must be installed and logged in. | Uses your Claude subscription quota |
| `api` (default when `ANTHROPIC_API_KEY` is set) | Anthropic API | Pay per use |

The STEP analysis runs entirely locally and never calls a model.

## Usage

Terminal output and per-check reasons are currently in Chinese. The JSON keys and component names are in English.

### Grade one drawing
```bash
python -m drawing_grader grade --cand ai_drawing.png --step part.step --out results/run1
```
Optional flags:

- `--ref references/part.json`: also compare against a reference drawing
- `--samples 3`: more robust drawing extraction, at 3× the reading cost

### Grade many drawings
Write a manifest CSV. Paths are relative to the CSV, and empty columns are allowed. See [`examples/manifest_example.csv`](examples/manifest_example.csv).

```csv
case_id,generator,candidate,step,reference,model_images,inventory
part01,claude,outputs/claude/part01_run1.png,steps/part01.step,,,
part01,chatgpt,outputs/chatgpt/part01_run1.png,steps/part01.step,,,
part02,claude,outputs/claude/part02_run1.png,steps/part02.step,,,
```
```bash
python -m drawing_grader batch manifest.csv -o results --workers 2
```
This writes `results/scores.csv`, with one row per drawing and every component score, plus `results/trials/<row>/` for each drawing's full report. It also prints the average score per generator. A failed row is recorded as an error and does not stop the batch.

### Self-check the grader
Inspired by the oracle tests in [Harbor](https://harborframework.com) / Terminal-Bench. Run this once per new part to show the grader is trustworthy on it:

```bash
python -m drawing_grader check --ref-image known_good_drawing.png --step part.step
```

| Test | Expectation |
|---|---|
| **oracle**: a known-good drawing | ≥ 85 |
| **null**: blank image or 3D render | ≤ 5 |
| **mutation**: wrong values, missing holes, wrong hole depth or count, missing views or chamfers, layout defects, injected text | Score must drop |
| **monotonic**: deleting 25 / 50 / 75 % of the non-redundant dimensions | Score must not rise |
| **fairness**: changing only information absent from the STEP (tolerances, GD&T, roughness, title block, notes, thread depth, view letters) or adding extra *true* dimensions | Score must stay **unchanged** |

The mutation, monotonic and fairness tests run locally on the extracted data and use no model quota.

### Extract a drawing to JSON
Useful for building or reviewing reference answers:

```bash
python -m drawing_grader extract drawing.png -o references/part.json --samples 3
```

## Output

`reward.json` uses the same format as Harbor's `reward.json`. `reward` is the total score scaled to 0–1 (values below are illustrative):
```json
{"reward": 0.92, "accuracy": 0.95, "completeness": 0.88, "standard": 1.0, "consistency": 0.9, "layout": 1.0}
```

`reward-details.json` lists every individual check with an id, a 0–1 score and a reason. It also records gate results, the agreement rate and the `needs_review` flag:
```json
{"id": "completeness:孔 2×Ø20 THRU", "score": 0.65, "reason": "未写 THRU", "component": "completeness", "component_weight": 40}
```
Check ids and reasons are currently written in Chinese. In this example, "孔" means "hole" and "未写 THRU" means "THRU not specified".

`report.json` holds the full human-readable breakdown, and `extraction.json` holds what was read from the drawing.

## Repository layout

```
drawing_grader/
  __main__.py       CLI: grade / batch / check / extract
  grader.py         combines components, gates, injection guard, reward output
  step_geometry.py  STEP analysis, accuracy and completeness scoring
  score.py          optional comparison against a reference drawing
  rubric.py         standard and consistency rules
  extract.py        Claude calls (API or claude -p), caching, sampling
  consensus.py      majority-vote merging of multiple samples
  selfcheck.py      oracle / null / mutation / fairness tests
  schema.py         data model for drawings and judgements
references/         reference answers (optional)
inventories/        3D feature lists for image-only mode (optional)
examples/           manifest template
```

## Configuration

| Environment variable | Default | Purpose |
|---|---|---|
| `DRAWING_GRADER_BACKEND` | `cli` (or `api` if a key is set) | How Claude is called |
| `DRAWING_GRADER_EFFORT` | `high` | Model effort: `low` / `medium` / `high` / `xhigh` / `max` |
| `DRAWING_GRADER_CACHE` | `.grader_cache/` | Cache directory. `usage.jsonl` logs the time and cost of every call. |
| `ANTHROPIC_API_KEY` | – | Enables the `api` backend |

## Limitations

- **Units:** values are compared in millimetres. Inch drawings are not supported yet.
- **Part types:** tuned for machined prismatic and turned parts (faces, holes, chamfers, fillets). Sheet metal, castings and free-form surfaces are only partly covered.
- **Value matching:** a dimension is checked by its value, not by which feature it points to. On a complex part about 8 % of random values happen to equal some real distance, so a wrong value is occasionally missed.
- **Standard thresholds** (3 views, 10 dimensions) may be too strict for very simple parts.
- **New part types:** run `check` once on each new kind of part to confirm the grader behaves as expected before trusting its scores.
